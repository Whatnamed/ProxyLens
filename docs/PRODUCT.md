# ProxyLens 产品需求与设计准则 (PRODUCT.md)

---

## 1. 项目定义与定位

**ProxyLens** 是一个面向 Windows 环境、深度结合 Mihomo (Clash Meta 内核) 的**本地代理流量审计与连接追踪工具**。

### 核心目标
> **让实际发生的代理流量尽可能可追溯、可解释，从而发现不必要的代理流量并辅助优化 Mihomo 分流规则。**

### 与普通“流量计费器”的根本区别
普通的流量统计工具只关注“总量消耗”（例如：今天消耗了 10GB 流量）。而 ProxyLens 的核心价值在于**审计与解释**，回答完整的因果链条：
$$\text{谁 (进程)} \longrightarrow \text{去了哪里 (域名/IP)} \longrightarrow \text{为什么走代理 (命中规则)} \longrightarrow \text{经过什么路径 (策略组)} \longrightarrow \text{实际用了哪个节点} \longrightarrow \text{消耗了多少流量}$$

## 2. 用户痛点与背景

当用户在 Windows 开启 TUN 模式或增强分流后，经常面临以下困惑：
1. **暗中产生的代理流量**：系统后台服务（如 Windows Update、NTP 时间同步、安全软件守护进程）、各类软件的后台遥测与自动更新，在不知情下被分流规则送入代理。
2. **规则死角与漏网之鱼**：大量未精细配置的域名或 UDP 流量命中 `MATCH` 兜底规则走代理，耗费节点流量甚至触发风控。
3. **连接即时性与不可回溯**：现有的 Mihomo 仪表盘（如 FLClash / yacd / MetaCubeXD 的 Connections 视图）仅显示“当前正在活跃”的连接，连接一旦关闭，所有元数据瞬间消失。
4. **旧方案“未知数据”黑盒**：过往方案中经常出现数十 GB 流量被粗暴归为“未识别/Unknown”，用户依然无法得知流量去向与产生原因。

## 3. 已经确定的产品原则 (Product Baseline)

以下原则作为 ProxyLens 的核心基线，指导所有功能与架构设计：

### 3.1 审计优先于统计
- 统计是聚合结果，审计是因果明细。
- 系统的首要任务是完整、准确地保留单条连接的元数据，流量聚合统计是建立在审计数据之上的二次能力。

### 3.2 优先观察真正的代理流量
- 必须明确区分连接类型：`DIRECT`、`PROXY`、`REJECT` 及其他特殊结果。
- 允许记录和查询 `DIRECT` 流量，但系统默认的分析重点、异常检测与报表展示必须聚焦于**实际经过代理节点**的流量。
- 严禁将所有经过 TUN 虚拟网卡的流量笼统视为“代理流量”。

### 3.3 历史连接必须可回溯
- 连接结束后，其元数据必须在本地可靠持久化。
- 用户可以在数小时、数天甚至数周后，精确查询当时某个时间段内发生过的历史连接。

### 3.4 “未知 (Unknown)”必须可解释
- 系统严禁出现大块模糊的“未识别流量”。
- 若某条记录信息不完整，必须给出明确的技术归因：
  - `MissingProcess`：Mihomo 未能识别进程（如特定封装或底层驱动转发）
  - `MissingDomain`：仅捕获到目标 IP，无 Host / Sniff Host
  - `MissingRule`：规则字段缺失或异常
  - `MissingChain`：代理链信息缺失
  - `CollectorStopped`：采集器未运行导致的监控中断
  - `ControllerUnavailable`：Mihomo API 暂不可达
- **特别要求**：采集器未运行期间的数据缺失，必须记录为“监控缺口 (Monitoring Gap)”，绝不允许伪装成“未识别流量”。

### 3.5 必须表达监控覆盖情况
- 系统必须能够清晰告知用户监控的健康度与完整性：
  - Collector 当前是否正常运行
  - Mihomo External Controller 是否可正常连接
  - 最近是否发生过采集中断
  - 哪些具体时间段属于监控盲区
  - 统计周期内的总体监控覆盖率估算

### 3.6 UI 不要求常驻，允许轻量后台 Collector
- 接受架构解耦方案：由极轻量的后台 Collector 负责常驻采集，UI 随用随开。
- Collector 不显示完整主窗口，低资源占用（低 CPU、低 RAM）。
- 当 Mihomo 未运行时，Collector 自动进入休眠/等待状态；Mihomo 恢复后自动重连并继续采集。
- UI 关闭后，后台 Collector 可独立继续工作，保证历史数据不中断。

### 3.7 只读原则 (Read-Only)
- ProxyLens 第一阶段**完全只读**，不介入代理配置控制：
  - 不修改 Mihomo 配置文件
  - 不自动修改分流规则
  - 不自动切换代理节点
  - 不修改 Windows TUN 模式、系统代理设置或网络路由表
  - 不主动阻断连接，不执行限速
- 未来可提供“规则优化建议”或“一键复制规则片段”，但必须由用户在外部配置中手动应用或显式确认。

### 3.8 本地优先与隐私边界 (Privacy by Design)
- 历史数据**默认仅保存在用户本地设备**，不进行任何云端遥测上传。
- **允许保存的元数据**：
  - 时间戳（起止时间、持续时长）
  - 进程信息（进程名、进程路径——若内核提供）
  - 网络元数据（Host、Sniff Host、目标 IP、目标端口、网络协议 TCP/UDP）
  - 分流元数据（命中 Rule、Rule Payload、Proxy Chain、Final Proxy、分流结果类型）
  - 流量数据（Upload / Download 字节数）
- **严禁采集与保存的隐私数据**：
  - HTTP 请求与响应 Body 正文
  - 网页内容
  - Cookie / Token / Authorization Header / 认证凭据
  - 请求 Payload / 参数明文
  - TLS 解密明文内容
- ProxyLens 的定位是元数据审计工具，坚决不做抓包解密或内容监控。

### 3.9 第一阶段不做底层网络抓包
- 第一阶段数据源完全依赖 **Mihomo External Controller 官方提供的 API**（如 WebSocket Connections / Traffic / Memory）。
- 暂时不引入以下底层技术：
  - Windows 过滤平台 (WFP) 驱动
  - WinDivert
  - 底层 Packet Capture (Npcap 等)
  - TLS 解密中间人
  - ETW 网络归因跟踪
  - 独立的 Socket 到进程匹配引擎
- 优先充分验证 Mihomo 原生数据的完整性与表达力。

### 3.10 第一版目标运行环境
- 优先支持：**Windows 11 + Mihomo 内核 + FLClash 客户端**。
- 架构设计保持通用性，避免与 FLClash 私有特性强绑定，但早期不为兼顾多系统而过度设计。

### 3.11 V1 界面语言与本地化
- 正式界面语言支持 English 与简体中文；语言属于全局 UI 偏好，可即时切换并在本地持久化。
- 只翻译界面文案；进程名、域名、IP、协议、原始数据字段值及其他技术证据保持原始值。
- `PROXY`、`DIRECT`、`REJECT` 等 canonical route values 在数据层保持英文；展示层使用统一的界面标签，不混用未经定义的临时译文。
- 日期与时间展示遵循当前界面语言；内部时间值、Query API 语义和筛选边界不因 locale 改变。

## 4. 核心功能范围

### 4.1 历史连接明细 (Historical Connections)
提供已结束连接的分页、检索与明细追溯能力，核心字段包括：
- **时间**：`start_time`（连接建立时间）、`end_time`（连接关闭时间）、`duration`（持续时长）
- **进程**：`process_name`（进程名）、`process_path`（进程绝对路径）
- **目标**：`host`（请求域名）、`sniff_host`（嗅探域名）、`destination_ip`（目标 IP）、`destination_port`（目标端口）
- **协议**：`network`（TCP / UDP / Type）
- **分流逻辑**：`rule`（规则类型，如 GeoIP, DomainKeyword, Match）、`rule_payload`（匹配内容）、`proxy_chain`（经过的策略组链路）、`final_proxy`（实际出口节点）
- **结果与流量**：`traffic_type`（PROXY / DIRECT / REJECT）、`upload_bytes`（上传字节）、`download_bytes`（下载字节）、`total_bytes`（总流量）

> *注：字段最终以 Mihomo 实际 API 稳定输出为准，设计阶段保持向下兼容。*

### 4.2 多维度聚合统计 (Multi-Dimensional Aggregation)
支持按以下核心维度进行流量（上传/下载/总量）与连接数聚合：
- **应用维度**：按进程名、进程路径聚合
- **域名与目标**：按请求 Host、根域名 (Apex Domain)、目标 IP 聚合
- **分流规则**：按 Rule、Rule Payload 命中排行聚合
- **策略与节点**：按 Policy Group、Final Proxy 消耗排行聚合
- **传输协议**：TCP vs UDP 流量分布
- **时间周期**：今日、昨日、最近 7 天、最近 30 天、自定义时间范围

### 4.3 待检查流量发现 (Audit Intelligence)
核心规则辅助引擎，通过透明、可解释的启发式规则，主动帮助用户定位异常代理连接：
1. **近期新观测到代理流量的进程**：在显式 baseline 窗口中未观测到代理流量、recent 窗口中观测到代理流量；不表示历史首次，也不判断进程可疑。时间比较要求完整 Coverage，并另提供按 bytes/hour 比较的进程代理增长发现。
2. **后台/安全软件目录匹配**：当前仅包含三条有来源依据的 Microsoft Defender 条目，必须同时匹配进程名与观测时的路径；不声称覆盖 NTP、Telemetry、Windows Update 或全部安全软件，不判断可信性。
3. **MATCH 兜底规则大流量**：未命中具体域名/IP 规则，掉入 `MATCH` 默认策略并产生显著流量的连接。
4. **宽泛 UDP 代理流量**：由于 `NETWORK,udp` 等宽泛规则被意外送入代理的高频小包或音视频连接。
5. **纯 IP 目标大流量**：缺乏域名信息且没有明确反查结果、走代理节点的大流量 IP 连接。
6. **突发大流量连接**：单条连接流量超过指定阈值（例如 > 100MB）且目标非预期。
7. **记录域名的分流窗口比较**：同一 exact recorded host 在 baseline 中 DIRECT > 0 且 PROXY = 0、recent 中 PROXY > 0；不表示长期行为或规则已被修改，recent 中混合的 DIRECT/REJECT 证据仍保留。

### 4.4 基础流量统计与未来增强
- **基础统计**：上传、下载、总量、连接数计数，支持各维度的 Top 排行榜。
- **未来增强规划**（不阻塞核心审计）：
  - 机场套餐周期与自定义重置日
  - 节点倍率配置与估算
  - 机场月度消耗模拟计算

## 5. 核心验收场景 (Acceptance Scenarios)

### 场景 A：后台 NTP 审计
- **操作**：Windows 系统后台触发时间同步，或杀毒安全软件（如 `HipsDaemon.exe`）向 `us.pool.ntp.org:123` 发起 UDP 同步。
- **验收要求**：系统能够完整记录该连接，保留进程名、目标域名、UDP/123、命中规则 `NETWORK,udp`、策略组链路、最终代理节点及上传/下载字节数；连接关闭或次日启动 UI 时仍能精确检索该条记录。

### 场景 B：代理下载大文件追溯
- **操作**：通过代理节点下载约 1GB 文件。
- **验收要求**：系统能清晰说明该 1GB 流量的具体归属（哪个进程、什么目标域名/IP、命中哪条规则、经过哪个策略组与实际节点），严禁出现大块无法解释的 Unknown 流量。

### 场景 C：DIRECT 大流量防误计
- **操作**：通过国内直连网络下载数 GB 内容（如 Steam 游戏下载或大文件分发）。
- **验收要求**：系统正确将其分类记录为 `DIRECT` 连接，不会将其计入“代理节点总消耗”中，保证代理流量数据的真实性。

### 场景 D：Collector 中断与缺口表达
- **操作**：主动停止后台 Collector 进程 1 小时后重新启动。
- **验收要求**：系统在时间线及覆盖率视图中明确标记这 1 小时为“监控中断缺口 (Monitoring Gap)”，并提示覆盖率下降，严禁将未监控期间的数据缺失推卸或伪装为“未知流量”。

### 场景 E：节点切换历史追溯
- **操作**：用户上午使用节点 A 产生流量，下午切换至节点 B 产生流量。
- **验收要求**：历史连接记录必须永久锁定当时发生时所走的真实节点 A 与节点 B，严禁因当前最新节点为 B 而错误覆盖上午的历史节点记录。

## 6. 明确不做的事项 (Non-goals)

为防止项目范围蔓延，第一阶段明确排除以下内容：
- ❌ 自己实现代理核心（依赖现有的 Mihomo）
- ❌ 替代 FLClash 等全功能代理客户端（不做配置管理、订阅转换、节点延迟测速界面）
- ❌ 底层网络抓包与网络数据包重组
- ❌ TLS 中间人解密与证书伪造
- ❌ HTTP/WebSocket 内容与负载敏感分析
- ❌ 防火墙与网络准入控制
- ❌ 广告拦截规则引擎（如 AdGuard DNS 拦截）
- ❌ 网络限速、QoS 流量整形与网络加速
- ❌ 自动、未经确认地修改用户代理配置文件或分流规则
- ❌ 机场订阅全生命周期管理
- ❌ 100% 精确模拟各大机场服务端的复杂计费逻辑
- ❌ 一开始追求支持 macOS / Linux / Android 等全平台
- ❌ 一开始适配所有代理内核（如 Xray / v2ray-core / sing-box）

## 7. V1 阶段验收标准

1. **零阻断与稳定性**：Collector 连续在后台静默运行 72 小时，内存占用稳定且 CPU 占用忽略不计，不影响 Mihomo 与宿主系统的网络稳定性。
2. **数据完整性**：在 Mihomo 正常运行期间，正常结束的 TCP / UDP 连接元数据 100% 捕获并落库，不丢包、不 double-count。
3. **因果可解释性**：审计页面能清晰展示完整的“进程 $\to$ 目标 $\to$ 规则 $\to$ 策略组 $\to$ 节点 $\to$ 流量”链路。
4. **中断显式化**：发生任何异常退出、Mihomo 重启或断网时，能够准确记录监控缺口。
5. **界面可用性**：UI 可随开随关，支持毫秒级响应最近 7 天内连接的多维检索与排序。
